# 반복 컴파일 최적화 측정 — 2026-10-22

## 변경

1번 개선(검사 도구만 빌드, 같은 업데이트 실행 안에서 재사용)을 적용한 상태가 비교 기준이다. 공통 Swift 소스를 컴파일하는 기존 명령에 `-whole-module-optimization -Onone`만 추가했다. 파일별로 반복되는 공통 소스 분석을 전체 모듈 단위로 묶으며, 런타임 최적화는 끈 상태를 유지한다. 별도 라이브러리 분리나 영구 캐시는 추가하지 않았다.

공통 소스를 사용하는 기본 도구·설정·진행창·업무 런처, 전체 시험 함수, 개별 업무/업데이트/전환/GUI 시험 및 후보 pin 시험에 동일하게 적용했다. 단일 파일이나 독립적인 소규모 바로가기 빌드는 그대로다. 시험 항목, 실행 순서, 서명·해시 검증, 설치 로직은 변경하지 않았다.

## 측정 방법

- 변경 전후의 Sources 내용이 모두 같음을 확인했다.
- 각 측정은 프로젝트 `.build/compile-suite-{before,after}-{1,2}` 아래 별도 소스 복사본에서 시작했다. 매번 `.build`가 없는 상태였으므로 후보 빌드처럼 새 컴파일러 캐시를 준비하는 비용을 포함한다.
- `CODEXSPLIT_SOURCE_ROOT`는 운영 소스 폴더로 동일하게 설정했다.
- `scripts/check.sh` 전체 실행을 순서대로 측정했다. 1회차는 변경 전→후, 2회차는 변경 후→전으로 실행했다.
- 합성 시험에 필요한 sandbox 권한을 사용했다. 실행 중인 업무 프로필 Codex 종료·재시작, 실제 업데이트 배치, 실제 프로필 변경은 실행하지 않았다.

## 검증 근거

- 대표 `app-opening` 시험의 compiler 작업 계획: frontend compile jobs 21개→1개.
- 대표 시험 컴파일 3회 중앙값: 10.090초→3.615초. 첫 측정의 캐시 준비 비용과 순서 효과가 있으므로 주 성과 지표는 위 전체 검사 비교로 삼는다.
- 변경 후 전체 검사 2회에서 기존 모든 시험 통과: 기본 119개, 앱·프로필·런타임·신호 시험, 자동화 22개, 전환 77개, 설치·교체 시험, 후보 pin 시험, 업무 GUI 상태 97개와 dispatch 3개 포함.
- 각 실행의 마지막 standalone 런처 서명 검증·번들 구조 검사 통과. 후보 앱은 열지 않았다.
- 변경한 shell 파일 문법 검사 및 `git diff --check` 통과.
- 1번 개선 기준 복사본과 비교하여 구현 차이가 compiler 옵션과 설명 주석뿐임을 확인했다. 기존 작업 중 변경을 보존했다.

실행별 전체 로그와 수치는 `.build/compile-suite-*/checks.log`, `.build/compile-suite-results.json`에 보관한다. 커밋·원격 push·설치·서비스 재시작은 수행하지 않았다.
